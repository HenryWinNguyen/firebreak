## Goal
Each fault scenario in SCOPE.md (S1–S6) can be switched on and off through the
admin API exactly as specified in CONTRACTS §2.2–2.3, and it causes a realistic
symptom.

## Mandatory reading
- `docs/CONTRACTS.md` §2.2, §2.3; `SCOPE.md` "Fault scenario library"
- The code T-011 merged in `shopfloor/`

## Patterns to mirror
- `shopfloor/common/` (from T-011) for middleware, auth and logging

## Definition of done
- [ ] `GET/POST /admin/chaos`, `POST /admin/chaos/reset`, `GET /admin/deploys` and `POST /admin/deploy` behave as in CONTRACTS, with bearer auth and 422 on an unknown flag
- [ ] S1: deploying an `orders` version ending in `-bad` sets the error rate to 0.1 (500s with a realistic stack-trace log line). The deploy shows up in `/admin/deploys` and `app_info.version`
- [ ] S2: `orders.db_pool_size=2` causes pool waits → latency and `db_pool_in_use` saturation under load
- [ ] S3: `orders.n_plus_one=true` switches to a per-item query path (latency grows with cart size)
- [ ] S4: `inventory.unavailable=true` makes inventory return 503, and orders logs dependency errors
- [ ] S5: `orders.leak_kb_per_request` retains memory per request (visible in RSS)
- [ ] S6: a bad `orders.redis_host` makes cache calls fail with connection errors in the logs, while the service degrades to the DB
- [ ] Tests for every flag (state changes, auth, reset)
