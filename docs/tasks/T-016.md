## Goal
S5–S7 ground truth (T-043) was written from code reading, not observed. Run each on the live stack
the way T-014 did S1–S4, and adjust the scenario's load/flag values and expected alerts to what
actually fires, so the eval grades against reality. $0: no LLM involved.

## Mandatory reading (before writing any code)
- `CLAUDE.md`, `docs/CONTRACTS.md` §2.3, §3.1
- `tests/integration/m1/test_scenarios.py` (reuse its helpers: reset, load generator, clean-wait, `startsAt` filter)
- `evals/scenarios/*.yaml`, `firebreak/evals/scenario.py`
- `shopfloor/orders/app.py` (leak, Redis provider, `SafeCache`), `ops/prometheus/rules/`

## Definition of done
- [ ] S5, S6 and S7 added to the m1 live test, driven from the scenario YAML (load the `Scenario`, apply `setup`,
      run `load`), with the same robustness rules as S1–S4 (reset in `finally`, no silent load failure,
      3 clean polls, `startsAt` after the fault, clears after reset).
- [ ] Each fires one of its expected alerts within its window. If not: investigate with PromQL, then change the
      scenario's values (flag value, rps, cart size, duration) or its `alerts` list to what is observed, and
      record the reason in a YAML comment. Never change shopfloor or the alert rules (a needed change there is
      reported to the lead with the exact diff).
- [ ] S7 control: the same load with no fault does not fire the S7 alert for S1–S6's purposes, i.e. S7's
      alert must come from load alone, not a leftover fault (document what you observe).
- [ ] S5 stays within host memory: report peak RSS of orders.
- [ ] Results table in the PR: scenario → alert → time to fire → clears → peak RSS (S5).
- [ ] PR description has a `## Progress entry` (builders don't edit PROGRESS.md)

```bash
FIREBREAK_INTEGRATION=1 uv run pytest -q tests/integration/m1 -s -k "s5 or s6 or s7"
```
