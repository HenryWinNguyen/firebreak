## Goal
S7 ("traffic spike, no bug") never fires: the driver's load generator is one asyncio process and tops out at
~120–440 rps on this Mac, and orders' 5m p95 peaked at 0.74 s (threshold 1 s). Henry chose (CP1, 2026-11-14) to try a
multi-process generator first, time-boxed; the fallback (a scenario-scoped capacity cap on orders) is a separate task
if this doesn't fire. Make the generator able to offer ~1000+ rps from several processes.

## Definition of done
- [ ] `Load.processes: int = 1` (1–8). With 1, behaviour is exactly today's (same class, same tests)
- [ ] With N > 1, load runs in N child processes (`multiprocessing` spawn context), each running the existing
      asyncio generator at `rps / N` with its own `httpx` client (same base URL, timeout and headers as the parent's); `prepare` (product list) happens once in the parent
      and is passed down. `halt` stops all children within a few seconds (Event + join with timeout, then terminate,
      logged; blocking joins go through `asyncio.to_thread`). Counters (`ok`, `http_errors`, `transport_errors`, `crashes`, first crash) are aggregated from the
      children, so `summary()` and `raise_if_broken()` work unchanged. A child that dies is a broken generator (fails
      loudly, never silently lower load)
- [ ] No orphan processes on any exit path (exception, guard trip, Ctrl-C): test that children are gone after halt
      and after an exception in the parent
- [ ] `s07.yaml`: `processes: 4`, `rps: 1200` (comment: tune live; the lead validates)
- [ ] Tests (no live stack): N=1 unchanged; N=2 aggregates counters from children against a local test HTTP server
      (or a fake transport if a server is impractical across processes: say which); halt/cleanup; child death fails
- [ ] PR description has a `## Progress entry`; note the max rps you measured locally against a trivial local server
      (informational only)
