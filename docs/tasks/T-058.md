## Goal
After an S5 run the T-052 reset (`leaked.clear(); gc.collect()`) left orders at ~1.5 GiB RSS and `HighMemory` kept
firing (2026-10-30), so the lead had to restart the container by hand. The buffers are `bytes` objects freed into the
allocator, which keeps the pages. Allocate the leak so freeing it returns memory to the OS deterministically.

## Definition of done
- [ ] Leak buffers are anonymous `mmap.mmap(-1, size)` regions, filled so they count toward RSS (touch every page).
      `release_leak` closes every mapping, then clears the list. Same `orders.leak_kb_per_request` semantics
- [ ] Shopfloor test (Linux and macOS): leak ≥ 64 MiB, measure RSS (`psutil` if already a dependency, else
      `/proc/self/statm` on Linux / `resource` fallback, skip with a reason where unmeasurable), reset, and RSS drops
      by at least half the leaked amount. Plus: after reset the list is empty and every mapping is closed
