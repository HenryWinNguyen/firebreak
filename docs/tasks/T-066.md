## Goal
Today a workflow only starts by hand. Make ingest start it: every firing, non-duplicate alert the grouper places goes to
`incident-<incident_id>` with signal-with-start (`SIGNAL_ALERT_ADDED`, payload `AlertAdded`), and the workflow waits in
`GROUPING` until the window closes (or a critical alert closes it) before triaging. Read the v1.7 grouping rule in
CONTRACTS §1 first: the Postgres grouper stays the source of truth for membership; the workflow only waits.

## Definition of done
- [ ] `load_context` fills `IncidentContext.window_closes_at` from the incident (timezone-aware; a naive value fails
      validation loudly)
- [ ] Workflow: `@workflow.signal(name=SIGNAL_ALERT_ADDED)` handler with its parameter annotated `AlertAdded`; its state
      (e.g. "critical seen") is initialised in `__init__` (signal-with-start delivers the signal before `run` starts).
      `load_context`, then in `GROUPING` wait until `window_closes_at` (timer from `workflow.now()`; `None` or past → no
      wait) or a `critical` `AlertAdded`, then **call `load_context` again** so alerts and services that joined during
      the window reach triage and every later agent. Signals after the window are logged and ignored (their alerts are
      in a new incident, or were already in the reloaded context). `GROUPING` is recorded via `set_incident_state` like
      every other state. Deterministic (no wall clock). Note in a comment the small residual race (API vs Temporal clock)
- [ ] `client.py`: `signal_alert_added(client, incident_id, AlertAdded)` using signal-with-start on
      `ORCHESTRATOR_TASK_QUEUE`, id `incident-<id>`, `id_conflict_policy=USE_EXISTING`, `id_reuse_policy=REJECT_DUPLICATE`. A workflow that already finished for that id (id reuse rejected) is
      logged at info and not an error
- [ ] API: after `ingest`, for each firing result with an `incident_id` (duplicates included: re-signalling is idempotent
      and repairs a signal that failed on an earlier attempt of the same webhook), call `signal_alert_added` with that alert's id and severity. The Temporal client is created lazily and cached
      (the API must start and accept webhooks with Temporal down); connect and each signal are bounded with
      `asyncio.wait_for` (default 5 s, setting) so a dead Temporal can't hold the webhook past Alertmanager's timeout. If signalling fails (Temporal unreachable), the
      webhook still succeeds (alerts are stored), and the failure is logged at ERROR with the incident id and alert id
      (never swallowed silently). Close the client in the lifespan if one was created
- [ ] Tests: workflow waits for the window (time-skipping env: no triage before the window, triage after); critical
      signal closes it early; post-window signal ignored; window already past or `None` starts at once; an alert that
      joins during the window appears in triage's `ctx.summary` (reload). API: created incident →
      signal-with-start called with the right id/payload; duplicate → called again; resolved → not called; Temporal
      connect hangs → webhook returns within the bound; Temporal error → 2xx +
      ERROR log (fake client). One end-to-end test: webhook → real `WorkflowEnvironment` → workflow running in GROUPING
- [ ] Existing T-064 tests still pass: the exact `states` assertions (`tests/workflows/test_incident.py` ~198, ~213,
      ~293) gain `GROUPING`; stub `load_context` returning `window_closes_at=None` means no wait
- [ ] PR description has a `## Progress entry`; note the follow-up "reconcile incidents with no workflow" (not built).
      `CONTRACTS.md` v1.7 wins where ARCHITECTURE §3 differs
